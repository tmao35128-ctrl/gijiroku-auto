# フェーズ構想と評価（第2回インプット）

> ステータス: **構想フェーズ**。実装は Phase 1 のみ着手予定。

---

## 1. フェーズ全体像

| Phase | 名称 | 公開範囲 | 主目的 |
|---|---|---|---|
| **1** | 社内レビューアプリ | ジヤトコ社員のみ | SharePoint からの脱却。貸出車のレビュー収集を習慣化する |
| **2** | 外部公開 | ＋販売店・関係企業（閲覧のみ） | レビュー資産を社外に見せる。QR / リンクで開ける |
| **3** | 販売店コネクト | ＋販売店（書き込み） | 「乗りたい」→ 販売店へ送客。相談・購入の実績をアプリに反映 |
| **4** | 地域プラットフォーム | ＋一般（検討中） | 試乗会・貸出予約・試乗レビュー・販売店レビュー |

※ Phase 2 と 3 は入れ替わる可能性あり（社内で送客の仕組みを先に検証する手もある）。

---

## 2. 各フェーズの中身

### Phase 1 — 社内レビューアプリ（スモールスタート）
現行の SharePoint + Forms + Power Automate をブラッシュアップし、Web アプリ化。

- ホーム：レビュー一覧（YouTube コメント欄型／星評価／いいね／並び替え）
- 投稿：ニックネーム・星評価・レビュー本文（全項目必須）
- 車種一覧：運行中（エクストレイル／オーラ 計7台）＋人気の日産車
- 静岡県販売店情報：一覧 → 押すと公式 HP へ
- 予約は既存 Forms のまま（アプリからはリンクするだけ）

**Phase 1 で追加を強く推奨するもの**
- **返却翌日のレビュー依頼リマインド**（Power Automate → メール／Teams に QR とリンク）
- **マイページ**（自分の貸出履歴と、レビュー未投稿の車の一覧）
- **管理ダッシュボード**（レビュー投稿率・車種別平均評価・開発部へ渡す課題リスト）
- **投稿フォームの「気になった点／不具合」欄**（開発部 FB の本来の目的がここ）

### Phase 2 — 外部公開
- 社外向け公開ビュー（社員名・社内情報を出さない表示モード）
- QR ランディングページ（プロジェクトの説明つき）
- **投稿の公開前チェック（モデレーション）** ← 社外公開する以上ほぼ必須
- OGP / シェアカード

### Phase 3 — 販売店コネクト（本命）
社員が「この車に乗りたい」と思ったとき、アプリから静岡の販売店へ直接つながる。

- 車種詳細に **「この車について販売店に相談する」** ボタン
- 販売店を選ぶ → 連絡手段を選ぶ（電話 / チャットボット / 来店予約）
- 会話・相談の記録を**実績としてアプリに反映**
- 購入したら**購入記録と購入元の販売店**を反映（販売店側から入力）
- 販売店向けの簡易管理画面（送客一覧・ステータス更新・実績登録）
- ジヤトコ側 KPI ダッシュボード（送客数 → 来店 → 試乗 → 商談 → 成約）

**最大の難所は技術ではなく「ジヤトコだけで完結しない」こと。**
販売店 1 社ずつにプロジェクト説明・アプリ説明・実績報告の依頼が必要。

### Phase 4 — 地域プラットフォーム（未整理）
- 静岡県の販売店の**試乗会**情報と申込
- **貸出車の予約**をアプリ内で完結（＝ Forms からの移行）
- 販売店で試乗した車のレビュー投稿
- 販売店そのものへのレビュー投稿 ← リスク高（後述）

## 3. ニーズ評価（率直な判定）

| Phase | ニーズ | 難易度 | 判定 |
|---|---|---|---|
| 1 | **高い** — 予約殺到＝すでに需要が証明済み。SharePoint の使いにくさは実在の課題 | 低 | **やるべき。最短で出す** |
| 2 | **中** — 社長の要望であり動機は明確。ただし「販売店が見て何が嬉しいか」が未定義 | 低〜中 | やる価値あり。ただし Phase 3 の前振りとして設計する |
| 3 | **非常に高い** — ここが唯一「三方にメリットが立つ」フェーズ | **高** | **本命。ただし段階的に** |
| 4 | **未知数** — 特に販売店レビューはリスクが利益を上回る可能性 | 高 | 保留。Phase 3 の結果を見てから |

### なぜ Phase 3 が本命か（三方のメリット）

| 立場 | メリット |
|---|---|
| **ジヤトコ社員** | 気になった車を、社内制度の延長で気軽に相談できる。営業に捕まる心理的ハードルが下がる |
| **ジヤトコ** | 福利厚生の効果を**数字で示せる**（レビュー○件・送客○件・成約○台）。予算継続と PoC 成功の根拠になる。日産グループ内での存在感も上がる |
| **静岡の販売店** | **確度の高い見込み客が名簿つきで来る**。実車に乗った後の人なので商談が早い。広告費ゼロの送客チャネル |
| **日産** | 「試乗 → 検討 → 購入」の一次データが取れる。ジヤトコからの品質 FB も同時に得られる |

**逆に言うと、Phase 1・2 だけでは販売店にメリットがありません。**
「レビューが見られる」だけでは販売店は動きません。Phase 3 の送客とセットで説明して初めて協力が取れます。

## 4. フィードバック（率直に 7 点）

### ① 最大のリスクは「レビューが集まらないこと」
機能ではなく運用の問題です。人は返却したら忘れます。
→ **返却翌日の自動リマインド（QR 付き）を Phase 1 の必須機能に**。
→ 投稿は 60 秒で終わる設計に（星をタップ＋一言でも投稿できる）。

### ② 「成功の定義」を今のうちに数字で決める
Phase 2 に進む稟議も、販売店を口説く材料も、全部ここから来ます。
例：レビュー投稿率 70%以上／月間閲覧 ○件／開発部への課題起票 月○件。
**この数字がないと Phase 2 以降は絶対に承認が下りません。**

### ③ Phase 3 の壁は技術ではなく「販売店の口説き」＝営業活動
1 社ずつの説明は非常に重いです。
→ **全店同時展開は必ず失敗します。まず 1〜2 店舗のパイロット。**
→ そこで「送客○件・成約○台」の実績を作り、それを持って他店に広げる。
→ 最初の 1 社は、ジヤトコと既に関係のある販売店を選ぶ。

### ④ 販売店とのシステム連携は「作らない」のが正解
販売店ごとに基幹システムが違い、API 連携は現実的ではありません。
→ **紹介コード方式**を推奨。社員が来店時にアプリの QR / 紹介コードを提示 →
   販売店は月 1 回、簡易フォーム（またはスプレッドシート）に結果を入力するだけ。
→ これなら販売店側の負担が最小で、実績データは取れます。

### ⑤ 購入記録は個人情報の扱いに最大限注意
「誰がどこで何を買ったか」は機微情報です。社内規程・個人情報保護法の確認が必須。
→ **第一歩は匿名の集計値だけを持つ**（今月の送客 12 件・成約 2 台）。
   個人に紐づけるのは、本人同意の仕組みを作ってから。

### ⑥ 販売店レビュー（Phase 4）は慎重に
店舗への低評価が公開されると、協力してくれた販売店との関係が壊れます。
→ やるなら「販売店に見えるが公開はしない」非公開 FB から始める。
→ 公開レビューは、関係が固まってから。

### ⑦ 一番の敵は「構想が大きすぎて Phase 1 が出ないこと」
今の構想はどれも筋が良いですが、全部を設計に入れると着手できなくなります。
→ **Phase 1 を最短で出す。** 目安 2〜3 ヶ月。
→ ただし **DB のテーブル設計だけは Phase 3 を見据えて作る**
   （後から `inquiries` / `purchases` / `dealers.staff` を足せる形にしておく）。
→ UI も、Phase 3 のボタンが入る余白を今のうちにデザインしておく。
